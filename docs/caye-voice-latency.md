# Caye Live Voice — latency investigation

Measured 2026-08-30 against `origin/main` @ `7f50cd54`. Every number below
came from a real call against the production Supabase project and the real
Anthropic API, not an estimate, unless explicitly marked.

## The pipeline as it actually runs

```
mic ──WebRTC──▶ OpenAI Realtime session (gpt-realtime-2.1, create_response:false)
  │
  ├─ input_audio_buffer.speech_started ────────────▶ bargeIn()
  ├─ input_audio_buffer.speech_stopped ────────────▶ (was not a dispatch trigger)
  └─ conversation.item.input_audio_transcription.completed
       │
       ▼  POST /api/founder/caye-direct/voice/turn
       requireFounder()                        Supabase auth round trip
       conversationalVoiceReply()              deterministic fast lane, else…
       runFounderThreadTurn(requestedMode:'auto')
         buildBackOfficeTurnContext()          serial DB chain
         runCayeDirectRouterTurn
           claude_subscription                 unavailable in prod (free, short-circuits)
           openai_codex_subscription           unavailable in prod (free)
           openai_api = gpt-5-mini             Chat Completions, NON-STREAMING
         persistAgentTurns / link / touch
         maybeGenerateThreadTitle()            was awaited
       │
       ▼  client runTurn()                     was awaiting a full thread refetch
       ▼  stt.speakReply(replyText)
       response.create{conversation:'none'}    realtime model RE-GENERATES the
                                               reply as audio — a second LLM pass
```

## Measured cost per turn

| Stage | Measured | Method |
| --- | --- | --- |
| `buildBackOfficeTurnContext` (warm) | **846–913 ms** | live, prod Supabase |
| ↳ system prompt | 48,083 chars ≈ 13.4k tok | live |
| ↳ history replayed | 43 msgs ≈ 4k tok | live |
| Tool schemas shipped every turn | **114 tools, 71,821 chars ≈ 20k tok** | live |
| **Total prefill** | **45,546 input tokens** | reported by the API |
| Model TTFT, production shape (sonnet-4-6 + 114 tools) | **2,288 ms** (total 3,763 ms) | live streaming call |
| Model TTFT, same context, no tools | 4,665 ms | live |
| Model TTFT, voice lane (haiku-4.5, no tools, 6 msgs, max 150) | **522 ms** (total 725 ms) | live |
| Model TTFT, voice lane (sonnet-4-6, same) | 1,010 ms (total 1,425 ms) | live |

Production is worse than the sonnet figures: `auto` lands on
`OPENAI_API_MODEL || 'gpt-5-mini'` through
`lib/model-router/backends/openai-compatible.ts`, which does
`await res.json()`. There is no first token — the whole completion,
including reasoning tokens, must finish before a byte comes back.

## Ranked contributors

1. **Typographic apostrophes routed every spoken greeting into the full
   tool loop.** Reproducible before the fix:

   ```
   "Hey Caye, what's up?"   grounding=false  fastpath="I'm here. What's up?"
   "Hey Caye, what’s up?"   grounding=true   fastpath=null      ← U+2019
   ```

   OpenAI's transcription models emit U+2019. Both
   `conversationalVoiceReply` and `requiresBusinessGrounding` matched only
   ASCII `'`, so the real transcript missed the fast lane *and* tripped
   `requiresGrounding` — which forbids a plain-text answer until a tool has
   run. "Hey Caye" cost ~1s; "Hey Caye, what’s up?" cost a full 46k-token
   round trip plus a mandatory tool call.

2. **`await maybeGenerateThreadTitle`** in the critical path of both the
   fast path and the full path: two DB reads plus an LLM call after Caye
   already knew what to say. Its own doc comment claimed it never blocked
   "the reply the founder is waiting on".

3. **The client awaited a full thread refetch before speaking**, with the
   reply already in hand.

4. **46k-token prefill on every turn**, 20k of it tool schemas a greeting
   cannot use.

5. **Non-streaming production backend.**

6. **Dispatch waited for `transcription.completed`** rather than acting at
   `speech_stopped`.

7. **The reply is re-generated by a second LLM** to be spoken.

Checked and ruled out: the two subscription health checks short-circuit on
`!isLocalBridgeEnvironment()` and are free in production; `execute.ts` and
the Anthropic backend do use prompt caching.

## Shipped (phase 1)

- `lib/caye-voice/spoken-text.ts` — shared punctuation folding, applied by
  the fast lane and the grounding classifier so both see the same string.
  Matching input only; the original transcript is what gets persisted.
- `lib/caye-voice/latency.ts` — AsyncLocalStorage stage trace, emitting one
  `[caye-voice] turn_timeline` line per turn. A hard no-op outside a voice
  turn, so the shared agent paths that also serve WhatsApp and cron are
  unaffected.
- `lib/caye-voice/client/voice-timeline.ts` +
  `POST .../voice/telemetry` — the browser half (speech end, transcript,
  round trip, first audible audio), re-shaped server-side to timings only.
- Fast-path persistence moved to `after()`, serialized per thread so two
  quick turns cannot land out of order.
- `responseStyle: 'voice'` restored (commit `4628b6c3` added it; a later
  merge silently dropped it) and wired to a 700-token ceiling plus spoken
  delivery guidance.
- Title generation no longer blocks a spoken reply.
- Client returns `replyText` when the POST resolves; the refetch continues
  in the background.
- A short factless preamble ("Checking now.") after
  `NEXT_PUBLIC_CAYE_VOICE_PREAMBLE_MS` (default 900 ms) so a tool-backed
  turn is never silent.

## Not shipped, and why

**Native speech-to-speech (`create_response: true`) with a narrow
capability bridge.** This is the right target and the session is already
90% of the way there: the realtime session is connected, mic audio is
streaming, `output_modalities: ['audio']` is set, and only
`create_response: false` plus a "you are a renderer" instruction stops the
model answering directly.

It is not shipped because flipping that flag lets the realtime model answer
business questions on its own authority, and the only thing holding it back
would be prompt text. `Products/Caye/CLAUDE.md` rules that out ("Do not
replace code-enforced safety with prompt instructions"), and this codebase
already has an incident where an LLM ignored its own ban list 7 times in 31
runs. There is also no `OPENAI_API_KEY` in the local environment, so the
realtime session config could not be exercised against the live API.

The design it should follow, verified against the current docs
(`developers.openai.com/api/docs/guides/realtime-conversations` and
`.../realtime-vad`, fetched 2026-08-30):

- `turn_detection: { type: 'semantic_vad', eagerness: 'low' }` for the
  conversational lane — `low` lets the founder finish a thought. `eagerness`
  is semantic-VAD only; `create_response` / `interrupt_response` exist on
  both and are conversation-mode only.
- Expose exactly four functions on the realtime session, never the 114-tool
  registry: `caye_query`, `caye_execute`, `caye_get_context`,
  `caye_request_approval`. Each is a thin call into the existing capability
  gateway; the realtime model never sees a tool name, a workspace id, or a
  risk tier.
- Anything that is not pure conversation must call one of those. The
  enforcement cannot be the instruction — it has to be that the realtime
  model has no other way to obtain a fact, because it is given no business
  state in its own context.
- Tool results return via `conversation.item.create` with
  `function_call_output`, then an explicit `response.create`.
- Barge-in stays as it is: `input_audio_buffer.speech_started` cancels
  server-side, and the client truncates with `conversation.item.truncate`.

The instrumentation shipped here is what should decide whether phase 2 is
still needed: if `speechEndToFirstAudioMs` lands inside the 1.2s acceptable
band for conversational turns after phase 1, the remaining work is the
tool-backed path, not the conversational one.

## Reading a turn

One session id spans both halves:

```
[caye-voice] turn_timeline   { sessionId, authMs, contextBuildMs, reasoningMs, toolMs, persistMs, totalMs, marks }
[caye-voice] client_timeline { sessionId, metrics: { speechEndToFirstAudioMs, … }, marks }
```

`speechEndToFirstAudioMs` is the number the performance targets are stated
in: under 700 ms ideal, under 1.2 s acceptable, for a conversational turn.
